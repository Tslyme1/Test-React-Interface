# DS Compose

Ты собираешь интерфейс из конструктора. Ты не проектируешь компоненты — ты их применяешь.

## Обязательный первый шаг

Дизайн-система здесь — внешний пакет `@uralmash/design-system`, и её документация
в npm-пакет не попадает. Поэтому сначала:

```bash
npm run ds:docs
```

Команда положит в `.ds-docs/` актуальные `INVENTORY.md`, `tokens/README.md`
и `CLAUDE.md` дизайн-системы. Прочитай **`.ds-docs/INVENTORY.md`**
и `.ds-docs/tokens/README.md`. Без этого не пиши ни строки вёрстки.

Если нужно свериться с фактическим API компонента — типы лежат
в `node_modules/@uralmash/design-system/dist/index.d.ts`.

## Систему править нельзя

Дизайн-система живёт в отдельном репозитории и прорабатывается отдельно.
Здесь её только применяют.

Поэтому шаги 3 и 4 алгоритма ниже заканчиваются не правкой системы,
а **остановкой и вопросом**: ни добавить вариант в существующий компонент,
ни завести новый компонент в системе отсюда нельзя.

Что делать можно: собрать композицию из существующих компонентов внутри `src/`
приложения — это экран, а не новый компонент системы. Граница простая: если
получившееся претендует на переиспользование в других продуктах — это заявка
в систему, её надо обсудить, а не писать молча.

## Алгоритм

Для каждого элемента будущего экрана:

1. Найди в инвентаре компонент с подходящей **ролью** — не с подходящим внешним видом. Роль важнее: «строка списка с действием» и «карточка» могут выглядеть похоже, но это разные компоненты.
2. Есть подходящий → используй как есть.
3. Есть близкий, но не хватает варианта → **остановись и спроси**: добавить вариант в существующий компонент или это действительно новый.
4. Ничего нет → **остановись и спроси**. Опиши предлагаемый компонент: роль, пропсы, варианты, состояния, чем отличается от ближайшего существующего.

**Никогда не создавай компонент молча.** Это единственное правило, нарушение которого разрушает систему целиком.

## Запрещено без исключений

- hex, `rgb()`, `hsl()` в коде компонентов
- произвольные значения: `p-[13px]`, `w-[247px]`, `text-[15px]`
- `style={{ }}` с размерами или цветами
- `margin` для расстояния между соседями — только `Stack gap`
- фиксированные высоты у блоков с текстовым контентом
- прямой импорт из `tokens/primitives` — только семантика
- собственные медиазапросы вместо брейкпоинтов системы

## Состояния — не опция

Каждый интерактивный элемент собирается сразу с полным набором: `default`, `hover`, `focus-visible`, `active`, `disabled`. Каждая область с данными — с `loading`, `empty`, `error`. Если состояние не описано в задаче, возьми поведение из инвентаря, а не придумывай.

## После сборки

1. Запусти `npm run check` — типы, линтер и E2E. Нарушения — не «замечания», а блокер.
2. Поле «Используется» в `INVENTORY.md` живёт в репозитории системы, отсюда его
   не правят. Вместо этого перечисли в отчёте, какие компоненты задействовал, —
   это уйдёт в систему отдельной задачей.
3. Отчитайся коротко:
   - какие компоненты переиспользовал;
   - где пришлось спросить и что решили;
   - какие состояния покрыл.

## Тон работы

Лучше задать три вопроса и собрать из готового, чем самостоятельно сгенерировать красивый экран с шестью новыми сущностями. Вопрос стоит минуту, лишняя сущность живёт годами.
