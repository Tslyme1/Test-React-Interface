# Передача интерфейса в разработку

Документ для разработчика, который берёт этот репозиторий в работу, и для того, кто
передаёт. Он отвечает на один вопрос: **что здесь готово, а что только выглядит готовым.**

Коротко: это UI-слой и контракт данных, а не приложение, которому не хватает бэкенда.
Разница существенная — см. раздел «Три места, которые надо удалить».

---

## 1. Граница ответственности

**Верстка и компоненты — зона дизайна.** Весь интерфейс собран из
[`@uralmash/design-system`](https://github.com/Tslyme1/design-system): отступы через `Stack`/`Box`,
типографика через `Text variant`, цвет — только семантические роли. Состояния
`hover / focus-visible / active / disabled` живут внутри компонентов системы.

**Правило для разработчика: новых визуальных компонентов не создавать.**
Не нашлось подходящего — это вопрос к дизайну, а не повод написать свой `<div className="card">`.
Реестр того, что уже есть, — `INVENTORY.md` в репозитории дизайн-системы, живая витрина —
Storybook там же. Обход системы «на один раз» не бывает одноразовым.

**Логика, данные, интеграции — зона разработки.** Ниже сказано, где именно швы.

---

## 2. Что действительно готово

- **Доменная модель.** [`src/types.ts`](src/types.ts) — `Project`, `WizardData`, `GeomData`,
  `GranData`, `ProdData`, `User`. Поля и их смысл уже зафиксированы; угадывать не нужно.
- **Страницы управляются пропсами.** `ProjectsPage` принимает `projects` и коллбеки
  `onOpenProject` / `onRemoveProject` / `onNewProject`. Источник данных можно подменить,
  не трогая верстку.
- **Состояние изолировано в хуках** — `src/state/useProjects.ts`, `src/state/useSession.ts`.
  Это и есть точки подключения бэкенда (раздел 5).
- **Экранная логика core-флоу**: поиск и сортировка в списке проектов, шаги визарда,
  открытие/закрытие drawer, тосты, пустое состояние списка.

---

## 3. Три места, которые надо **удалить**, а не дорабатывать

Это главный риск передачи: код выглядит рабочим, но рабочим не является.

### 3.1 Авторизация — заглушка, и небезопасная

[`src/state/useSession.ts`](src/state/useSession.ts):

- внутрь пускает **любой** логин с любым паролем (`known ?? { ...создать пользователя на лету }`);
- кладёт объект пользователя **вместе с паролем** в `localStorage` открытым текстом;
- ролей по существу нет — поле `role` есть, проверок прав нет нигде.

Файл выбрасывается целиком. Остаётся только форма входа
([`src/pages/LoginPage.tsx`](src/pages/LoginPage.tsx)) как верстка.
Тестовые доступы из README (`ivanov/1234` и пр.) — демо-реквизит, не «первые пользователи».

### 3.2 Расчёты — фиктивные

[`src/domain/estimates.ts`](src/domain/estimates.ts) честно пишет об этом в шапке файла.
Значения вида `D/2`, `H − l2` подставлены, чтобы экран результатов выглядел посчитанным.
Настоящая методика подбора дробилок — предмет работы инженера; это не «формулы, которые
надо уточнить», это заглушка на месте продукта.

Интерфейс сейчас явно предупреждает пользователя, что оценки иллюстративные. Убирать
предупреждение можно только вместе с появлением настоящих расчётов.

### 3.3 Проекты не сохраняются

`useProjects` держит всё в `useState`. F5 — данных нет. Ни localStorage, ни API.

## 4. Чего в верстке нет вовсе

Это не дефекты, это неначатая работа. Перечислено, чтобы не обнаружилось в середине спринта.

| Чего нет | Что это значит |
|---|---|
| **Роутинга** | Навигация — `useState` в [`src/App.tsx`](src/App.tsx). Нет URL, нельзя дать ссылку на проект, не работает кнопка «назад» браузера. |
| **Валидации по существу** | `required` у `Field` — звёздочка и блокировка кнопки при пустом поле. Числовые поля визарда — свободные строки: ни диапазонов, ни единиц, ни проверки `Dmin < Dmax`. Правила — отдельная договорённость с инженером. |
| **Асинхронных состояний** | Компоненты системы умеют `loading / empty / error`, но в приложении нет ни одного асинхронного вызова, поэтому по экранам эти состояния не разведены. Появится API — решение «что показываем, пока грузится, и что при ошибке» нужно принять на каждом экране **вместе с дизайном**, а не на ходу. |
| **Тестов** | Ни одного, раннера в `package.json` нет. |
| **Обработки ошибок** | Нет error boundary, нет единого места показа серверных ошибок. |

## 5. Как это превращается в «приложение, которому не хватает бэкенда»

Порядок важен: каждый шаг оставляет приложение рабочим.

1. **Ввести слой доступа к данным.** `src/api/` с типизированными функциями
   (`listProjects`, `createProject`, `updateProject`, `removeProject`, `login`, `logout`).
   Сначала — реализация поверх текущих моков. Ни одна страница про `fetch` не знает.
2. **Перевести хуки на этот слой.** `useProjects` / `useSession` начинают ходить в `src/api/`
   вместо `useState`. Появляются `isLoading` и `error` — и вот тут разводятся состояния из
   таблицы выше. Верстка страниц не меняется.
3. **Зафиксировать контракт API.** Типы из `src/types.ts` — исходник для схемы. Отдельно
   описать то, чего в UI-модели нет: пагинация списка проектов, коды ошибок, права по ролям.
4. **Добавить роутинг** (`react-router`): `/login`, `/projects`, `/projects/:id/:step`.
   Правится `App.tsx` и навигационные пропсы страниц. После этого ссылка на проект работает.
5. **Заменить мок-авторизацию на настоящую** — раздел 3.1. Токен, refresh, редирект
   неавторизованного, проверка прав по `role`.
6. **Вынести расчёты за интерфейс.** `estimates.ts` заменяется вызовом расчётного сервиса
   (или серверной методики). Форма результата — та же, экран не переверстывается.
7. **Подключить persistence и убрать все «—»** в полях `oreIn` / `oreOut` / `throughput`
   ([`src/state/useProjects.ts`](src/state/useProjects.ts)) — сейчас там прочерки-заглушки.

После шагов 1–2 фраза «приложению не хватает бэкенда» становится правдой. До них —
неправда, и передавать с такой формулировкой не надо.

## 6. Объём: что сверстано, а что нет

Перенесён **core-флоу**, а не интерфейс целиком.

**Сверстано и закрыто:** вход/выход, список проектов (поиск, сортировка, удаление, пустое
состояние), создание проекта, инженерный визард на 3 шага, drawer результатов.

**Не сверстано** (см. бэклог в [README.md](README.md)): упрощённый режим, ситовый анализ,
интерактивная SVG-диаграмма камеры дробления, регистрация и восстановление пароля,
админ-панель «Пользователи и роли», папки/теги и корзина, экспорт в Excel и печать,
~15 второстепенных модалок и поповеров прототипа.

**Этих экранов нет — и разработчику их верстать не нужно.** Понадобился экран из бэклога —
запрос в дизайн. Иначе система разъедется ровно там, где её никто не проверяет.

## 7. Зависимость от дизайн-системы — поправить до передачи

Сейчас в `package.json`:

```json
"@uralmash/design-system": "github:Tslyme1/design-system"
```

Ссылка на ветку без версии. Значит, любой push в `master` дизайн-системы меняет интерфейс
приложения при следующем `npm install` — молча и в разное время у разных разработчиков.

Для прототипа приемлемо, для команды нет. Минимум — ставить git-теги и ссылаться на тег:

```json
"@uralmash/design-system": "github:Tslyme1/design-system#v0.1.0"
```

Нормальный вариант — публикация пакета в реестр (в т.ч. приватный / GitHub Packages).
Тогда обновление дизайн-системы становится осознанным шагом разработчика с видимым диффом.
