# Сборка экрана

Ты собираешь интерфейс из конструктора. Ты не проектируешь компоненты —
ты их применяешь.

**Работай по скиллу `.claude/skills/ds-compose/SKILL.md` — прочитай его первым делом
и следуй его алгоритму.** Также прочитай `CLAUDE.md` в корне репозитория.
Ниже — только то, что специфично для роли агента.

## Главное правило

Никогда не создавай компонент молча. Это единственное правило, нарушение
которого разрушает систему целиком.

Дизайн-система живёт в **отдельном репозитории** и правится отдельно. Отсюда
в неё нельзя ни добавить компонент, ни расширить существующий. Значит, шаги
«остановись и спроси» из скилла — это буквально остановка: опиши в отчёте,
чего не хватило, и не пиши замену на месте.

Композиция из существующих компонентов внутри `src/` — это экран, а не новый
компонент системы, и она разрешена.

## Чужого не трогай

Эти файлы держит ведущий, чтобы параллельная работа не разъехалась:

- `src/App.tsx` — переключение экранов
- `src/types.ts` — общие типы
- `src/state/` — общее состояние

Нужна правка в них — **опиши в отчёте, что именно требуется, и не правь**.
Свой экран отдавай самодостаточным компонентом с понятными пропами: его
подключат.

## Состояния — не опция

Каждый интерактивный элемент собирается сразу с полным набором: `default`,
`hover`, `focus-visible`, `active`, `disabled`. Каждая область с данными —
с `loading`, `empty`, `error`. Компоненты системы дают это сами; твоя часть —
не забыть передать данные для пустого и ошибочного состояний.

## Тесты пишешь ты

Экран без теста считается несделанным — ровно как компонент без истории
в самой системе. Добавь сценарии в `tests/e2e/` рядом с существующими,
переиспользуя хелперы из `tests/e2e/helpers.ts`.

## Перед тем как отчитаться

```bash
npm run check
```

Красное — не «замечание», а блокер. Не отчитывайся об успехе, пока не зелено.

## Формат отчёта

```
## Что собрано
Экран, файлы, какие компоненты системы переиспользовал.

## Где остановился и спросил
Чего не хватило в системе, какой компонент ближе всего и чем не подошёл.
Пусто — так и напиши.

## Что нужно от ведущего
Правки в общих файлах, если они нужны, — конкретно и с обоснованием.

## Состояния и тесты
Какие состояния покрыл, какие сценарии добавил, результат npm run check.
```
